Proposal · nine candidates against your own tests

Candidate primitives

Each one run through the tests in your README. A module if two sensible projects would disagree about wanting it, if it names a vendor or a business domain, if it brings a dependency the core does not carry, or if removing it still leaves a working CMS. Core if something else cannot work without it, if core would need to know it exists, or if it changes the shape of content, auth, tenancy or delivery. Two of these fail the module tests, and saying so is more useful than nine green ticks.

Candidate What it adds Verdict Because
MediaBarakoCMS.Media
 Crops, focal points, variants and reference counting on top of the existing IFileStorage. Module Brings an imaging dependency core should not carry, and a headless API for a mobile app may not want it.
FormsBarakoCMS.Forms
 Public form definitions, submissions stored as content, spam gate, notification on submit. Module Removing it leaves a working CMS. Worth building because Umbraco charges €250 per domain for it and your roadmap already promises it free.
RedirectsBarakoCMS.Redirects
 A 301 and 410 map, written automatically when a slug changes, served ahead of delivery. Module Named in #108. Subscribes to the slug-change event that core already emits, so it needs no core change at all.
SeoBarakoCMS.Seo
 Meta fields per type, sitemap.xml, robots.txt, canonical URLs, an Open Graph payload on delivery. Module Also #108. A treasury or a membership system wants none of it, which is the first test passing cleanly.
McpBarakoCMS.Mcp
 An MCP endpoint whose tools are generated from the content schema and routed through existing RBAC. Module Names a protocol and brings its SDK. Your roadmap has it at 3.26.0 and calls the current position "behind, not ahead".
Search.PostgresBarakoCMS.Search.Postgres
 Ranked full-text search with tsvector and GIN, no embedding model and no Ollama to run. Module The honest middle between core's keyword match and the AI module. Most deployments want this and not a GPU.
NotificationsBarakoCMS.Notifications
 An in-app feed for the things the admin currently discovers by accident: bounces, failed workflow runs, unbalanced journals. Module Subscribes to events other modules already emit. The one caveat: it wants a projection, and the contract cannot give it one yet.
Reviewapproval, sign-off
 Draft, review, changes requested, approved. The screen above. Core Fails the module tests: it changes the shape of content status and delivery has to know an approved-but-unpublished state exists. Same reason Workflows is correctly core.
Localizationlanguage variants
 One entry, many language variants, with fallback and per-variant publish state. Core Changes the shape of content and of delivery, which are contracts other modules stand on. A one-way door: retrofitting variants later is a data migration.

The blocker worth fixing first

Notifications, and any future module that needs to fold a stream into a read model, cannot exist because IModuleSchema exposes only For<T>(). Your own DECISIONS entry already flags this as the thing to change first if a module ever needs a projection. Three of the nine above want one, so that moment has arrived.

What I would build in this order

Modules screen first, because it is small, answers #185, and makes every later module visible the day it lands. Then Mcp, because the roadmap already dates it and the admin needs somewhere to put agent keys. Then Media, which unblocks the editor experience more than anything else on the list. Redirects and Seo are a weekend each and close #108.
