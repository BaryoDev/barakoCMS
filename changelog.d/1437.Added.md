- **CI upgrades a 5.9.0 database that holds data, and `docs/upgrading-to-6.0.md` lists what to change.** The `Upgrade from 4.x` job now also starts the released 5.9.0 image, pinned by digest, and seeds a content type that is event sourced and one that is not (with entries), a workflow, a role, a group, a redirect, a connector, a station, an API key, and a second tenant with CDN purge settings. It upgrades to the working tree's build, reads every record back, runs the stored workflow, then boots 5.9.0 again and reads them back from it. The read back compares fields (redirect paths, connector `baseUrl`, station capabilities, API key scopes, workflow actions, tenant name and status) and pages through each list. The script refuses a digest whose build commit is not the one the `v5.9.0` tag names. No migration follows 5.9.0, so `db-assert` has to pass as the database stands, and a schema change shipped without a file under `migrations/` fails there. `scripts/test-check-ports.sh` runs the read back, the empty plan decision and the digest check against canned answers, and `scripts/test-upgrade-plan.sh` covers the plan from 5.9.0. The live seed and upgrade run only in CI. The job has a 30 minute timeout. The guide covers the settings, start checks, limits and compose defaults a 5.9 install has to act on, each with its pull request. Its sections for #1383, #1384, #1385 and #1402 say they land with those issues and are not in the code yet.
