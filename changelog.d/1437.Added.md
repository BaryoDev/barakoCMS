- **CI upgrades a 5.9.0 database that holds data, and `docs/upgrading-to-6.0.md` lists what to change.** The `Upgrade from 4.x` job now also starts the released 5.9.0 image, pinned by digest, and seeds a content type that is event sourced and one that is not (with entries), a workflow, a role, a group, a redirect, a connector, a station, an API key, and a second tenant with CDN purge settings. It upgrades to the working tree's build, reads every record back, runs the stored workflow, then boots 5.9.0 again and reads them back from it. No migration follows 5.9.0, so the check asserts `db-assert` passes as the database stands, and a schema change shipped without a file under `migrations/` fails there. `scripts/upgrade-check.sh` takes a 5.9 `FROM_VERSION` with an empty plan, `scripts/lib-upgrade-data.sh` holds the seed and read-back, and `scripts/test-upgrade-plan.sh` covers the empty plan. The guide covers the settings, start checks, limits, compose defaults and removed members a 5.9 install has to act on, each with its pull request.
