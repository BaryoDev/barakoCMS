- **Superuser migrations run with a pinned search path, and restores run as the app role.** The hand-run migrations that need a superuser run with `PGOPTIONS='-c search_path=pg_catalog,pg_temp'`, so they use only built in functions and operators, and `scripts/upgrade-check.sh` runs them that way. The five rollback files on the owner list set the pin themselves. A restore now runs the owner job first (`run --rm --no-deps postgres-extensions`), drops the `CREATE EXTENSION` and `COMMENT ON EXTENSION` lines from the stream, and loads the dump with `PGOPTIONS='-c role=barako_app'`, so the app role owns everything it creates. `scripts/restore-db.sh` does this when the stack has the job and restores as the owner, saying so, when it does not. `docs/backup-and-restore.md` has the commands for the production and quickstart stacks, and `scripts/restore-check.sh` and `scripts/offsite-backup-check.sh` restore this way in CI. `scripts/restore-check.sh` also boots the API as the app role with database enforcement on and compares the policies and forced row level security before the dump and after the restore. From 6.0 a new migration does not need a superuser. Run ad hoc SQL as the app role, never the owner. See "Database roles" in `docs/deploy-in-production.md`.
