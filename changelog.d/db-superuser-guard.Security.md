- **The API refuses to start as a database superuser outside Development.** At startup, before it touches the schema, the API reads its own role. It stops when the role is a superuser, has `BYPASSRLS`, or is a member of `rds_superuser`, `azure_pg_admin` or `cloudsqlsuperuser`, the admin roles of the managed Postgres services. The error names the role and the reason, and points at `scripts/db-app-role.sql`, which creates a role without superuser. If the role cannot be read, the API stops too. A superuser is never bound by the row level security policies, so connecting as one switches them off. To run as a superuser on purpose, for example a throwaway container, set `Database:AllowSuperuser` (`Database__AllowSuperuser`) to `true`, in any letter case. The API then logs one warning at each start. A blank or `false` value keeps the refusal, and any other value (`yes`, `1`) keeps it too and the error says the value is not recognised. `docker-compose.hub.yml` now runs the role job and connects as `DB_APP_USER`, and requires `DB_APP_PASSWORD`. `k8s/04-role-job.yaml` creates the role for the Kubernetes manifests, and `k8s/02-secret.yaml` connects the API as that role. Every startup guard takes Development from the environment the host was built with (`IHostEnvironment`), and a host that registered none counts as Production. See "Database roles" in `docs/deploy-in-production.md`.
