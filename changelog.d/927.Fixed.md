- **A field's `validationRules` were stored and never applied.** A type author who set
  `{ "max": 100 }` got a 200 and every entry above 100 was stored anyway. Every entry write now
  checks `min` and `max` on number and date fields, and `minLength`, `maxLength` and `pattern` on
  text fields, and answers 400 naming the field and the rule. `regex` is read as `pattern`, and a
  field that sets both is refused. A pattern is matched anywhere in the value unless it is anchored
  with `^` and `$`, and a match that runs past 250 ms fails the write. `requiredWhen` makes a field
  required only while a condition on other fields holds, in the form permission conditions use:
  `{ "Kind": { "_eq": "Company" } }`, with `_eq`, `_ne`, `_in` and `_nin`, and
  `{ "Age": { "_lt": 18 } }`, with `_lt`, `_lte`, `_gt` and `_gte` comparing numbers and dates. A
  compared value that is missing, or is neither, leaves the field optional. Saving a type refuses an
  unknown rule name, a bound of the wrong kind, a `min` above its `max` and a pattern that does not
  compile or is longer than 500 characters. Only the fields a request adds are checked, so a type
  that already stores a rule a save would refuse still accepts a new field. An import leaves a
  field alone when the target already stores it with the same rules, so a bundle exported from a
  tenant imports back into it. That stored rule is skipped on entry writes. Stored entries that break a rule keep reading, and only new writes are
  checked. On start the API logs a warning per tenant listing the types whose stored rules now
  apply and the types carrying a rule that is skipped (#927, #810).
