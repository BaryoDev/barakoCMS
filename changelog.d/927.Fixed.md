- **A field's `validationRules` were stored and never applied.** A type author who set
  `{ "max": 100 }` got a 200 and every entry above 100 was stored anyway. Every entry write now
  checks `min` and `max` on number and date fields, and `minLength`, `maxLength` and `pattern` on
  text fields, and answers 400 naming the field and the rule. A pattern is matched anywhere in the
  value unless it is anchored with `^` and `$`, and a match that runs past 250 ms fails the write.
  `requiredWhen` makes a field required only while a condition on other fields holds, in the form
  permission conditions use: `{ "Kind": { "_eq": "Company" } }`, with `_eq`, `_ne`, `_in` and `_nin`.
  Saving a type refuses an unknown rule name, a bound of the wrong kind, a `min` above its `max`
  and a pattern that does not compile or is longer than 500 characters. Stored entries that break
  a rule keep reading, and only new writes are checked. A rule stored before this release that a
  save would now refuse, such as `regex`, is skipped on entry writes, and the type has to be
  imported again with the rule corrected before a field can be added to it. On start the API logs
  a warning per tenant listing the types whose stored rules now apply and the types carrying a
  rule that is skipped (#927, #810).
