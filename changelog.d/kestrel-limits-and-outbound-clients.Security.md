- **Kestrel connection and header limits are set on purpose, and every outbound HTTP client is accounted for.** A fresh start sets a 15 second request headers timeout, 10000 concurrent connections and 1000 upgraded connections, with the header size, header count, 130 second keep-alive timeout and 240 bytes per second minimum request body rate written down. `Kestrel:Limits:*` overrides each (see `docs/deploy-in-production.md`), and the two minimum data rates are set through `:BytesPerSecond` and `:GracePeriod`. `RequestLimits:MaxBodyBytes` is the one body size key, so `Kestrel:Limits:MaxRequestBodySize` is refused at startup. The caps are per process and behind a proxy such as Caddy count the proxy's connections, not users; raise `MaxConcurrentUpgradedConnections` when more than 1000 realtime WebSocket clients connect at once. An architecture test lists every `AddHttpClient` registration and every `CreateClient` call: a registration must have the outbound address guard as its primary handler and a timeout, or be named with the reason its target is set only by the operator, and a caller must pass a name constant. The one client a tenant or admin can aim (`ExternalApi`, used by webhooks, connectors, CDN purge and sign-in providers) was already guarded. The AI embedding client now has a 30 second timeout and a 1 MB response cap, and a webhook response body read has a deadline, so a receiver that sends headers and then stalls no longer holds a workflow run.
