- **Edit the lifecycle of an existing content type.** `PUT /api/content-types/{name}/lifecycle` replaces a stored type's states, initial state and transitions, with a `dryRun` that stores nothing. It needs `manage_content_types` and the version the edit started from as `If-Match` (428 without it, 412 when stale, read from the new `version` on `GET /api/content-types` or the `ETag` of the last edit), takes the type lock exclusive and writes the audit row `contenttype.lifecycle.changed`. An edit that removes or renames a state an entry holds, or changes the initial state of a type with entries, is refused with 409 and a `blockers` list with each state and its count (entries with no stored state count under the initial state, state names compare ignoring case). It is refused too when it removes or changes a transition that a role grants, a workflow is triggered by or makes, a rule runs on, or an unfinished workflow run carries, or removes or renames a state that a rule, a uniqueness rule or a date schedule names. A type a module seeded keeps its seeded states, transitions and initial state while that module is registered (kind `module`; additions stay allowed). Core records them per tenant and type in the new `mt_doc_module_seeded_types` table, created by `migrations/5.9.0/module-seeded-types.sql`; an email link to such a transition is a warning. Config apply and bundle import still refuse a changed lifecycle, and now name the route. See `docs/approval-by-configuration.md` (#1375).
