- **`GET /api/modules` reports which modules an instance registered.** Nothing did. A deployment is
  core plus whatever modules the host opted into in `AddBarakoCMS`, and there was no way to ask an
  instance which ones those were, so an operator, an agent and a client library each had to guess.
  Read straight off the container, which is what the host actually booted with rather than a list
  maintained alongside it.
- **Name and contract version per module, and nothing else.** A module knows its configuration
  section and its assemblies, and therefore its file paths on the host; none of that describes the
  module, it describes the deployment, and a module list is already reconnaissance. A test asserts
  the property names on each item are exactly `name` and `contractVersion`, so a field added later is
  a reviewable line rather than a leak.
- **The usual collection envelope, ordered by name.** Not a bare array: the root type of every
  collection response is frozen for 4.x. A host running no modules gets an empty list and a 200, not
  a 404, because a 404 is what a route that never shipped looks like.
- **`Roles("SuperAdmin", "Admin")`, matching `Features/Monitoring`,** rather than a capability. Every
  name in `SystemCapabilities` covers a management surface this endpoint neither reads nor writes,
  and a new one would not reach an existing Admin at all: `DataSeeder.ApplyCapabilityDefaults` leaves
  a role that already holds capabilities alone, so a name added after the backfill never arrives, and
  a deployment running `Auth:LegacyRoleFallback=false` would lock Admin out with nothing in the diff
  to show for it.
