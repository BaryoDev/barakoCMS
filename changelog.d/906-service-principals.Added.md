- **Service principals, capability scopes and read-only keys for API keys.** A key can act as a service principal in its tenant, so it keeps working when the person who made it leaves. A caller can only give a principal, bind a key to it, or move keys to it roles whose capabilities they hold themselves. A `cap:<capability>` scope reaches an endpoint gated on that capability, and a `bcms_ro_` key refuses every write. Platform, user, role, tenant, key, station, config and connector management capabilities cannot be given to a key. The rollback script revokes read-only and principal keys so a rollback never widens access. A principal key does content work (create, update, status, schedule, rollback, list, get) with the principal's roles, and the audit row names the principal. Person-only routes such as `/api/me` answer a clean 401 or 403. See `docs/api-key-service-principals.md`.
