- **CI starts the production stack, the secrets stack, the quickstart and a 5.9.0 volume, and fails unless the API runs as the app role.** After the API is healthy, the checks assert that every API session uses `barako_app`, that the role has no superuser and no `BYPASSRLS`, that everything in `public` (tables, sequences, views, materialized views, foreign tables, functions and the schema itself, apart from extension members) belongs to it, and that `pg_stat_statements` is installed with no refused extension in the API log. A second run of the `postgres-extensions` job changes no owner and no role attribute and reports `0 objects changed owner`; a table made by hand as the owner moves to the app role on the next run, and the app role reads and writes it from another container with its password. The secrets check also starts the API with a `db_connection_string` whose password is not the app role's: the API never becomes healthy, its log shows the authentication failure, and no password appears in any service's log. `scripts/quickstart-runtime-check.sh` runs the quickstart's job and API from a copy of the folder with no host port. `scripts/compose-upgrade-check.sh` starts the `docker-compose.prod.yml` and image of v5.9.0 with the API connected as the owner, writes content through the API, then runs the "Upgrading" steps from `docs/deploy-in-production.md` against the same volume and checks that the API is healthy as the app role and the old content reads back. A new test fails if any tracked file outside `scripts/db-app-role.sql` and its quickstart copy contains a `CREATE EXTENSION` statement.
