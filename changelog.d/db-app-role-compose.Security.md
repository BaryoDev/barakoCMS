- **The production and quickstart compose files run the app role script, and the API connects as that role.** The `postgres-extensions` job now runs `scripts/db-app-role.sql` (the quickstart's copy) as the database owner before the API starts, and the API waits for it with `condition: service_completed_successfully`, so a failed job stops the API from starting. The API connects as `DB_APP_USER` (default `barako_app`) with `DB_APP_PASSWORD`, a role with no superuser, so the row level security policies bind it. The policies exist only when `Tenancy:DatabaseEnforcement` is on, which is off by default. `DB_APP_PASSWORD` is required: the compose files refuse to resolve without it, and the API refuses an example value, with a message that names `DB_APP_PASSWORD`. If you set `DATABASE_URL`, it wins over the connection string, so point it at the app role too. With `docker-compose.secrets.yml` the app role's password goes in a new `secrets/db_app_password` file for the job, and `secrets/db_connection_string` names the app role and the same password. The nightly backup dumps with `--no-owner --no-privileges`, so run `docker compose up -d` after a restore to give the app role the tables back, and `restore-db.sh` now checks the archive, drops and recreates the database before it restores, and stops at the first failed statement. If the restore fails after the drop, it leaves the API stopped. The development files `docker-compose.yml` and `docker-compose.hub.yml` stay on the owner role. See "Database roles" in `docs/deploy-in-production.md`.
